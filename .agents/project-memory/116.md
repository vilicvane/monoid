# Notifications for pending actions

[user] After committing SSH session renewal, investigate how incoming requests can notify the phone. The scope is all operations that need user action. For WalletConnect, that means all supported signing requests; SSH signing is one kind, not the feature boundary. This is a feasibility investigation, not an approved backend deployment or protocol change.

[agent] The APP currently has no native remote push integration. Its WalletKit `session_request` handling and Home pending actions already process authenticated, current requests when the APP runs. Those listeners alone cannot show a reliable notification while the WebView is suspended or the process is absent.

[agent] Use a shared notification delivery path for pending actions, with WalletConnect as the first source. It must cover the existing EVM message, typed-data and transaction signing; Solana message, single/batch transaction and sign-and-send; and SSH signing. A push is a short-lived hint to resolve an action from its source, not a separate approval or a copy of the action. Keep APP admission, review, expiry and signing rules authoritative. An arriving RPC alone does not imply user action; read-only queries and routine session updates should remain quiet. Future action sources should reuse device registration and tap handling.

## Minimal feasibility test

1. Use the documented [WalletConnect Push URL path](https://docs.walletconnect.com/wallets/more/push-notifications.md) with a wallet project, public HTTPS URL and the [open-source Push Server](https://github.com/reown-com/push-server) or a compatible server. The relay sends signed webhooks; verify them before dispatching. APNs/FCM sending credentials remain server-side.
2. Use the [Capacitor push plugin](https://capacitorjs.com/docs/apis/push-notifications) for device permission, token and notification taps. iOS needs the APNs capability and correct sandbox/production environment; Android needs FCM setup. Register and refresh the token at the configured server using the existing WalletKit Core's persisted `crypto.getClientId()`. The installed JS `registerDeviceToken` always posts to hosted Echo and does not check HTTP status; use direct registration with the chosen server and check its response. Implement token replacement and opt-out with the documented unregister path when building the feature.
3. Start with the generic visible notification (`always_raw: false`). [The Push Server spec](https://specs.walletconnect.com/2.0/specs/servers/push/spec#register-client) describes a generic alert for `wc_sessionRequest` (tag 1108). This path needs no native decryption or second WalletConnect client. On tap, keep the intent until the router and WalletKit are ready. Match to a live request using the supplied topic/ID if available; when ambiguous, open Pending Actions. Run the existing expiry, authorization and NFC approval path. Push payloads cannot authorize or reconstruct a request. An already admitted request interrupted by process death must retain the existing ledger behavior, not resume card work.

## Open decision and validation

- WalletConnect signing methods share `wc_sessionRequest`, tag 1108, with read-only `monoid_sshGetKeyMetadata`. SignClient supplies `rpcMethods` in publish metadata to the relay, but the documented push webhook and upstream server schema expose only `topic`, `tag`, and encrypted `message` (plus legacy fields). The push server cannot distinguish inner RPCs using those fields. Compare signed callback field names and tags from EVM, Solana and SSH signing plus metadata-only and session lifecycle traffic on a test project. Do not log bodies or rely on undocumented fields. If the callback lacks a supported action discriminator, investigate moving our read-only traffic outside tag 1108; for example, negotiated `wc_sessionEvent` has tag 1110, which the Worker could ignore even though the current SDK still sets `prompt: true`. Any cross-client change needs its own review. The desktop Agent is not the push trigger for the product. Do not give the Worker WalletConnect session keys. On-device decryption/filtering is a separate approach; [iOS requires Apple approval](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.usernotifications.filtering) to reliably silence alerts in a notification extension.
- Exercise foreground (no duplicate system banner over the existing prompt), locked, background, and notification-tap cold start. Check notification permissions, late/duplicate delivery, and expired, interrupted or already handled requests. Use each action's own deadline; the desktop's default SSH wait of 90 seconds is only one case. A longer transport TTL never reopens an expired approval.
- The installed SDK and published specs were inspected. Current Dashboard settings, live callback contents, actual APNs/FCM delivery and cold-start acceptance have not been verified. No push service, credentials, configuration, APP code or Agent protocol was changed.

## Cloudflare Worker candidate

[user] Delegated the investigation and suggested a Cloudflare Worker for the eventual push service.

[agent] Prefer a separate `workers/push` service with the device registry, relay webhook verification and retry deduplication, independent of Authority. A local Miniflare/workerd fixture verified the WalletConnect Ed25519 framing (`timestamp.byteLength.rawBody`) with synthetic keys, including a UTF-8 byte-length case. Raw and legacy forms validated; a modified body, missing signature and changed timestamp were rejected. The two documented tag-1108 fixtures had identical visible fields. This validates the runtime and documented shape, not the production relay callback. The public relay key endpoint returned a hex Ed25519 key; use the real key only for live testing.

[agent] Worker `fetch` can use FCM HTTP v1 for Android. Prefer testing iOS direct APNs from the hosted Worker first, because Apple's provider API requires HTTP/2, and local `workerd` and hosted Worker egress differ. A [Cloudflare maintainer discussion](https://github.com/cloudflare/workerd/issues/4841) reports this exact APNs distinction; `node:http2` is a stub in Workers. An unauthenticated request to the APNs sandbox with a synthetic token can verify transport without sending a notification; then test actual delivery separately. If hosted direct APNs is unsuitable, FCM can forward to APNs with iOS Firebase Messaging, FCM tokens and an APNs key configured in Firebase. No hosted probe or provider call was made in this investigation.

## First implementation and Android validation boundary

[user] Requested implementation, chose Android FCM for the first physical test and approved the existing WalletConnect wallet project for validation while the APP is unpublished.

[agent] `workers/push` verifies audience-bound JWTs from the APP's existing persisted Core identity and checks Ed25519 signatures over the original callback bytes. Each device registry records current topic IDs, their session expiry and whether all negotiated methods are signing methods. Keep callback receipt hashes for bounded deduplication; never store encrypted request bodies, device credentials in logs, or WalletConnect session keys in the Worker. The generic APNs/FCM notice is short-lived. Workerd tests use mocked providers. An additional local interoperability check used the actual installed Core to generate a registration JWT and verified registration, signed callback, mocked OAuth/FCM delivery, replay suppression and opt-out end to end.
