# Monoid app development

Source: `../records.md`, records 13, 14, 25–38, 42–46, 62, 64, 69, 70, 84–89 and 94–100. Treat these records as authoritative and keep them up to date.

- The app (Ionic React + Capacitor, iOS and Android) drives the card applets of the sibling repo `monoid-javacard`, which owns the card protocol. The app mirrors its commands as x-value schemas in `src/@lib/monoid/monoid-applet.ts`, on top of the generic `CBORApplet`/`Applet` transport in `src/@lib`.
- The app installs cards from bundled applets in `src/@assets/applets` (+ `@applet-bundle.ts`), copied by `npm run prepare:applets` from `../monoid-javacard/build/javacard`. `npm run android`, `ios:sync` and `build:web` run it automatically; build the firmware from a clean commit first and commit the refreshed applets with the app change that mirrors it, or app-installed cards keep the old protocol (records 94, 97).
- Card maintenance (fresh, update, reinstall) can always Start over once it has written to the card: it reinstalls every applet from the bundled applets and keeps the recovery archive and card identity; untouched plans are just discarded; batches cannot restart (record 95).
- A popup menu of two or more action buttons wraps them in `<Buttons data-popup-animation-group>` (8px), like the Card page menu and `ConfirmPopup`; never place such lists directly in `DetailsPopup` (record 96).
- The project is old: point out whenever the user's choices conflict with the interactions its existing code implies.
- The phone's HTTP development WebView is not a secure context: `crypto.randomUUID` is unavailable even when it works in Node or desktop localhost. Use the shared `createFlowId()` from `@utils` for flow IDs; it uses `crypto.getRandomValues`, which remains available over HTTP. Preserve the same constraint for QR/NFC scan IDs. For route regressions, test the real route initializer with `randomUUID` absent; a mocked button handler misses this failure. The user chose project-memory guidance, not a lint restriction (record 46).
- When a wallet list is the main content of a page (including Transactions wallet selection), use the shared roomy layout by default. Embedded account summaries opt into `WalletAccountList`'s `compact` spacing; `compactContent` separately controls the gap between tags and address.
- Empty states (record 64): an empty main list shows only `ViewPlaceholder` and drops its section label; an empty list inside a list uses `KeyListItem` + `KeyListPlaceholder`; `InfoMessage` is for notices, not emptiness. Identifier-plus-alias headers follow the Safe key header: `ViewHeaderIdentifier` and an alias tag with `viewHeaderTagCSS` as direct `ViewHeader` children (Security Key does this for the card and Seed); multi-card flows (Copy, Sync, Extend, Setup) keep `CardPreview`.
- Card naming: name a specific card (ID tag, alias, "Scan card …") only where the operation really is about that physical card (Card page, Sync card popup, a retry that must reach the same card). Data that syncs across bundle cards (Security Key, OTP) never singles out a card in headers or status. Where a card is named, use the alias when set, with the ID after it in scan prompts.
- Multi-card steps (records 79, 81): cards live inside the active step's grid, never a big card plus a small-card grid. `CardPreview` `$scan`: `next` (border in the card's color plus a 2px ring at 35% of it) only for the one specific card to scan, `pending` (white) for cards still needing a scan, `ready` (dimmed) for finished ones. Waiting cards read "… later". The card to scan is shown by its style, never by an ID on a button.
- Flow completion (record 74): multi-step flows pop their steps (and any card preview or grid) out, then show only `OperationComplete` with a neutral back button. A `Step` takes the color of the current step's default button.
- Message blocks (`InfoMessage`/`WarningMessage`) are notices, never headings. Lists stay as they normally are: no wrapper boxes for the common case. Exceptions (e.g. skipped items) are appended after the normal list under a labeled divider (yellow warning icon, normal-color text, no count). A card popup header is the title plus a line of card ID and bundle tags (`ViewHeaderIdentifier`).
- Warning prompts (records 77, 78): several notices go in `ConfirmNotices` (numbered), a single one stays a paragraph; notices are real risks or required actions, never procedure steps. Ask choices about an added card when it is added (record 75). A scan for a specific card names it (`scanCardPrompt`).
- New flows and choices follow existing patterns first (records 84, 85). The user rejects invented UI. Copy the key derive steps:
  - selectors (`SegmentedControl` capsules, all the same height) and inputs in the step body;
  - the footer button confirms;
  - a done step shows `summary`.

  Setup cards' None / Cards / Authority capsules sit in each mode's first step. Authority owners are provider-native IDs and the bundle name is optional (record 89); "authority" is lowercase mid-sentence. Pickers copy the Bitcoin recipient picker. A row with an icon uses the shared 36px `Symbol`. The Authority account display (`AuthorityAccountInfo`) is identical in the app and on the hosted sign-in page (`workers/authority/web`), which reuses app components through documented adapters. Authority mode is card-first (Scan card → Choose bundle → Add cards) and every Authority request uses the card's own `Hello.authority` (record 100).

- Card operations use the shared layer (records 69, 70): `removeItems`/`setItemAlias`/`acceptMatchingItem` (item-operations), `CardItemNotFoundError`/`CardItemExistsError`, `probeApplet` (only `6A82` is missing), `isOperationCancelled`, `assertSameCard` (ID + public key; bundle only for Copy/Sync/backup/bundle flows) and `card-pins`, `readCardContents` with feature decoders, `MultiCardSeries`/`scanNextCards`, and `useCardOperation` for single-operation pages. Card cache invalidation is automatic through `CardStore.observeApplet`; never call `cardStore.forget` by hand after a write. Firmware has no backward compatibility: `EXISTS` on an existing index, `{removed}` from Remove, OTP accounts as one HMAC-mapped `0xF201` item.
- Verify from the repo root with `npx tsc --build --pretty false` and `npx prettier --check <files>`.
- Run ESLint from `src`, e.g. `Push-Location src; npx eslint --report-unused-disable-directives '<path>'; Pop-Location`. From the root it fails with "TSConfig does not include this file". Quote `@`-prefixed paths in PowerShell.
- `npm run lint` is clean on main (record 62); keep it error-free. Cross-directory imports go through `index.js` barrels per `@mufan/import`; when a barrel gains an export, update tests that mock that barrel path.
- Branch `archive/security-key-cloud-backup` holds the unmerged Security Key phone-backup exploration (CloudKV plugin); do not reintroduce it on main without a new request.
- Ionic Android live reload restores its `AndroidManifest.xml.orig` backup on exit: stop the session before editing the native manifest, or restore the manifest from git afterwards (record 86). Returning from another app no longer reloads the page when nothing changed, thanks to the dev-only `scripts/vite-hmr-reconnect.mjs` (Vite 7.0.6 only; record 99).
- Use Node 22.12+ and Capacitor 8.5.3. `npm run ios:sync` builds web assets and regenerates the iOS SPM dependencies; avoid hand-editing generated `CapApp-SPM`. `npm run ios` opens Xcode; Xcode 27 launches simulators through Device Hub.
- After `npm run build`, run application tests with `node --experimental-test-module-mocks --test tests/*.test.mjs`. The native plugin packages have independent XCTest targets; simulator checks do not establish NFC or Secure Enclave behavior. Core iOS decisions and remaining physical-device checks are in `../29.md`.
- The shared `MonoidUITests` scheme verifies first camera authorization on a real iPhone, resetting only Monoid's camera permission and preserving app data and other permissions. First authorization must wait for an actual app-activation notification after requesting access, because the reply can precede deactivation while activity snapshots still appear active.
- Both QR scanners resume on foreground with a fresh scan ID after successful camera cleanup; never restart a dismissed/leaving scanner or one that already accepted a result. The Bitcoin scanner dismisses through the popup's outside/back behavior without a Cancel button. Only main-scan link processing shows the loading spinner; cancelling does not. These QR rules do not permit NFC operation replay.
- QR recovery keeps the preview at full size under a static cover, then fades that cover after the first native frame is ready. Entry zoom belongs to the first scan, not foreground recovery.
- The app-level Passkey experiment was fully removed, including Home/account UI, local metadata storage, Passkey-specific card wrappers and the failed iOS provider/notification handoff. Preserve existing generic card P-256, Safe and NFC features. Direct NFC belongs in a card FIDO applet; remote transport remains undecided. Read the historical lessons in `../43.md` before resuming: standard FIDO QR hybrid requires BLE service-data advertising unavailable in the inspected iOS public API, and shared result storage does not prove delivery to a website. Do not reintroduce an inactive Passkey entry or old metadata management just to retain experiment code.
