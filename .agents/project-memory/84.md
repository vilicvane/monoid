# Authority bundle UI (record 84)

Request (user, 2026-10-27): imagine the real ways users add cards to an Authority bundle, choose the best interaction, UI and layouts, and implement it.

## Journeys considered

| Journey                                                    | Who                                                                               | Verdict                                                                            |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| New cards straight into an Authority bundle                | Someone setting up blank cards who wants recovery without a second member present | Primary: Setup cards gets an Authority mode                                        |
| An existing card with items, not in any bundle             | Someone adopting the Authority later                                              | Card page actions → Join Authority bundle (same flow, card prepared)               |
| Replacement or extra card for an existing Authority bundle | Lost card, new member                                                             | Same flow, pick the existing bundle; then the existing Sync                        |
| A card already in a card-created bundle                    | Moving to the Authority                                                           | Same flow; scanning it shows the existing reset confirmation (Join never replaces) |
| Organization owner provisioning cards                      | GitHub organization owner                                                         | Same flow with the organization owner; GitHub connection is a later package        |
| A separate Bundles/Authority console page                  | Power users                                                                       | Rejected for now: a new top-level concept for a rare task                          |
| Join chained into Install applets                          | —                                                                                 | Rejected: hidden inside maintenance                                                |

## Chosen design

- One flow, the existing `setupCard` route with a bundle mode: `none | card | authority`. When the mode isn't fixed by the entry point, a `Bundle` row with a segmented control (None / Cards / Authority) replaces the Create bundle toggle, disabled once a card is added, like the toggle. Card page actions keep Create bundle (`card`, fixed) and add Join Authority bundle (`authority`, fixed, the card prepared). It is shown only when the card is in no bundle and trusts an Authority (cached from Hello).
- **Mode capsules in steps (user: "put the selection capsules in steps").** When the mode isn't fixed, the None / Cards / Authority `SegmentedControl` sits at the top of the current mode's first step body, as derive's chain selector does. It replaces the earlier labelled Bundle row:
  - None: in Set up card.
  - Cards: in Add cards, above the grid; disabled once a card is added.
  - Authority: in Choose bundle.

  Authority therefore has two steps. Sign-in lives inside Choose bundle, because a separate Sign in step would finish instantly for an existing session and hide the capsules. An `InfoMessage` names the Authority (signed out) or the signed-in account. The footer is Sign in, then Continue; the summary is `owner / name`, e.g. `Account / personal` (record 87). The owner capsules stack under the mode capsules, like derive's BTC sub-selector.

- Earlier draft, superseded by the bullet above: Authority mode had three steps, built like the key derive steps (user: "be extremely careful when you see new patterns and UIs", "see also key derive steps"). Standard controls sit in the step body, the footer's primary button confirms, and a done step shows `summary`. A first draft was rejected because it introduced patterns the app doesn't have: tapping a row to advance, labels in step titles, bare-icon list rows, a "+ New" row, and ad-hoc popups.
  1. **Sign in.** An `InfoMessage` names the Authority host. The footer button Sign in opens the hosted login in the system browser, which returns on `app.monoid://authority/callback`. Summary: the account login.
  2. **Choose bundle.**
     - An owner `SegmentedControl` (Account / Wallet / GitHub), only when there are several namespaces.
     - A bundle-name input: the shared input with a trailing action, generalized from derive's `ResettableInput`. It's prefilled with the latest bundle, and its list button opens a Choose bundle popup built like the Bitcoin recipient picker.
     - A "Members can add cards" `Toggle`: disabled and showing the bundle's policy for an existing name; for a new name, enabled with an `InfoMessage` that the policy is permanent.
     - Continue moves on. Summary: the bundle name.
  3. **Add cards.**
     - A card grid like Create bundle step 1, with the prepared card ringed as next. Each tap joins at once: Hello, check the card's Authority equals the signed-in one and that it's in no bundle (or already this one), fetch the packet in the same NFC session, authenticate the Secret PIN, Join, then compare the hash with the service's.
     - Blank cards go through the existing install and PIN-setup path, and the just-set Secret PIN is reused. A card in another bundle gets the existing reset confirmation.
     - Joined cards are dimmed with the description "joined". Done finishes with OperationComplete.
- Sign-in session: an Authority service holds the bearer in memory only (record 85). Sign-in opens the system browser app; the pending login (state, PKCE verifier, expiry) survives a cold start so the callback can still complete, without ever blocking a new attempt (record 87). Callbacks that are cancelled, expired, duplicated or unrelated are rejected. A 401 returns to signed out.
- Errors name the cause:
  - no Authority on the card;
  - a different Authority URL;
  - Join 6985: a different Authority key;
  - 409: the bundle exists with another policy;
  - an expired session.
- Not in this round: GitHub connection for organization owners, group names on the Card page, Add card from an Authority member's page, and re-issue after a member's fresh install.
