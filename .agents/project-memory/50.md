# Card record compatibility

[user] Initially authorized temporary `key` / `keyPrefix` to `metadata` / `metadataPrefix` conversion until the cards were copied. After the separate Identity Bundle incompatibility was identified, explicitly requested removing this adapter immediately. Independently, incompatible data should be discarded one record at a time instead of preventing the entire flow.

[agent] Runtime evidence from the Android card scan showed the raw List response returning `key`, `index` and `secret`, with a ten-byte `key` and no `metadata`. The application had already moved to the new fields. The derivation reader rejected the missing source metadata before reading the record body; that error was not evidence of a corrupt body.

[agent] The temporary implementation was isolated at the Monoid protocol boundary and is now removed. It normalized old List/View/Export fields, preserved omitted versus empty metadata and sent matching aliases in Create/Import/List. Do not reintroduce it without a new request; current commands use only `metadata` and `metadataPrefix`.

[agent] Removed the temporary adapter, factory substitution, Copy/Sync/derivation/maintenance size wrappers and temporary tests. The persisted maintenance archive's existing `key` field is a separate stable storage format; retain its mapping and saved archive checksums independently of card protocol compatibility.

[agent] Long-term behavior: classify incompatible application records with `InvalidCardItemError` and skip only that class at collection boundaries. Retain compatible items and progress. Preserve unsupported target indexes so skipping cannot turn an existing record into a missing item and cause it to be overwritten. Unknown opaque types are not automatically invalid. Never swallow NFC loss, PIN/permission failures, cancellation or uncertain mutation outcomes. Skipping a record does not delete it from the card. Destructive maintenance must not treat a filtered list as a complete recovery archive.

[user] Confirmed the previously failing physical card opened Card with the temporary adapter. The intended next operations were Bundle extension followed by synchronization to another card; extension failed at Join, before data transfer.

[agent] Before removal, TypeScript, production web build and all 2,692 application tests passed. The active Android applet instance was checked offline and emitted matching new/old metadata fields. Physical acceptance of that temporary adapter covered scanning into Card only. After its removal and the extension UI step consolidation, TypeScript and all 2,685 remaining application tests passed.

[agent] Join diagnosis: requester `7d643176`, approver `2dd3db90`, new target `6a1590ae`. Existing approval produced a 376-byte enrollment with header `01 00 04 04`, matching the old three-byte header and four 65-byte members. The target's recorded Identity image matches the current `601f7058…` load hash, whose header is four bytes including flags. It computes 259 member bytes instead of 260 and `Bundle.assertPublicKeysLength` throws `CryptoException.ILLEGAL_VALUE`; the phone reported `INTERNAL / CryptoException / reason 1`. New format would require 377 bytes. Both use version 1, and the HPKE context also changed, so APP cannot repair the authenticated packet by inserting a byte. The user will have JavaCard handle this; no card mutation or firmware fix was performed here.
