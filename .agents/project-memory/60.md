# Security Key account backup and card recovery

## Scope and status

[user] Wants Security Key account information in phone storage that can be backed up. Another chat will implement the storage plugin. This task is limited to verifying the chain after plugin data is read: matching a card/Seed, restoring account records and using the original credentials. Plugin storage, system backup and plugin interfaces are outside this task.

[agent] Feasibility was verified on 2026-10-25. No new card command is required. The APP recovery feature and UI have not been implemented or approved through this investigation; do not describe the proposed sequence below as shipped. This concerns the card's FIDO Security Key Applet, independently of the removed app-level Passkey provider experiment in record 43.

## Data and identity

[agent] A Security Key account is a public, non-Secret `0xf101` record. Its card index is `F101 || credentialId[0:8]`; metadata is the 32-byte scope followed by `SHA256(rpId)`. Its version-1 CBOR data retains the full random 32-byte credential ID, RP hash/ID, user ID and optional names, resident flag, 65-byte P-256 public key and scope.

[agent] Retain the exact `index`, `metadata` and `data` bytes, with optional alias; derive display fields from the validated record. Also retain the exact derivation domain bytes associated with each scope. Domain is the applet's derivation parameter, not the website's RP domain. It is present in the applet grant but absent from the credential record. A scan can establish this association for the active grant; an inactive scope whose domain was never captured cannot be assigned the current/default domain by guesswork.

[agent] Use the full scope and credential ID to identify a stored credential. The ten-byte card index is its destination storage address, not a sufficient global identity. Do not merge or deduplicate by website/user name. Distinct registrations can have the same displayed account.

[agent] Scope derives from the Seed contents and exact domain, independently of Card ID, applet installation token or local Seed index. The APP can compute it with the existing public `readSecurityKeyScope` / `viewKey` path; extracting a Seed is unnecessary. The credential key additionally depends on the RP hash and full credential ID. The original Seed, domain and complete credential record are all needed: Seed alone cannot reconstruct random credential IDs, and public account records alone cannot recreate the private key. Seed recovery remains a separate flow; account backups need no PIN, Seed or private key.

## Proposed APP-to-card sequence

[agent] The following is the implementation proposal supported by current code/protocol, not an additional user-approved UI specification:

1. Read and validate records individually. Omit incompatible entries as in record 50, while retaining their occupied destination indexes; never treat an unreadable existing record as absent or overwrite it. NFC, authentication and cancellation errors remain operation failures.
2. Scan the destination, use the shared Access PIN session, inspect available Seeds and compare the candidate Seed/domain's derived scope with the saved records. Card ID and source Seed index are only optional hints, not recovery requirements. If no matching Seed exists, stop before claiming the account is usable; restore the Seed separately.
3. Check Security Key installation and its grant. A missing or reinstalled applet needs explicit Enable Security Key on card with the matching Seed and saved domain. Reinstallation generates a new installation token, so set a fresh grant instead of replaying the old token hash. Do not silently replace a different active Seed/domain configuration.
4. Plan writes using the shared Copy/Sync credential validation and merge rules: missing index means create; identical metadata/data means skip; different content under the same index means conflict without overwrite. Keep separate indexes separate. Prefer explicit restoration of missing accounts over unconditional automatic union, which can resurrect intentionally deleted or replaced registrations from an old backup.
5. Create public records with the original bytes and `secret: false`, then read back to verify acknowledged writes. Public record restore and applet authorization require Access PIN, not Secret PIN. Reuse shared validation/merge without inheriting the whole Sync flow's Secret PIN requirement. Interrupted or uncertain writes must be reconciled by reading the card, never blindly replayed.

## Operational limits

[agent] One Security Key Applet has one active Seed/domain grant. Records from other scopes may coexist but remain inactive; changing back restores their eligibility. The FIDO PIN is separate from Access/Secret PIN and is not restored by account records; a new applet needs its FIDO PIN configured through a FIDO client if user verification is required. Current `signCount` is always zero, so recovery does not require a shared monotonic counter.

[agent] Website registration operates directly against the card and bypasses the APP. Newly registered accounts cannot enter the phone's collection until the APP scans them. Restoring record bytes cannot undo a website's revocation of the original credential; successful local signature verification does not establish real website acceptance.

## Implementation gaps at cb4b4fd

[agent] `SecurityKeyView` holds a temporary snapshot and clears it on leaving. `readSecurityKeySnapshot` parses records but drops the original CBOR and metadata after decoding. Add lossless record retention, scope/domain association and the restoration planner/UI when implementation is requested. Existing Seed configuration preserves a current grant's domain or uses the default for a new grant; recovery must explicitly accept the saved domain on a fresh card. Do not silently substitute the default.

[agent] Record 61 closed the lossless-retention and storage gaps: snapshots keep `record` bytes and alias, and `SecurityKeyBackupStore` stores accounts plus scope→domain entries in `CloudKV`. The restoration planner and UI are still not implemented.

## Validation evidence

[agent] TypeScript and 47 existing APP Security Key / merge tests passed. Five JavaCard simulator tests passed: the four existing scope tests plus a temporary transfer test. The latter registered resident and nonresident credentials, serialized only their public index/metadata/data as Base64, restored them onto a fresh simulated card, and used a different local Seed index. Wrong Seed or wrong domain returned `NO_CREDENTIALS`; matching Seed/domain and a fresh grant produced signatures verified against both original registration public keys, including resident discovery. Readback matched the original record bytes.

[agent] The temporary test used synthetic Seeds and accounts and ran only in `CardSimulator`. It was not added to permanent source and was cleared with the later normal APP build. No physical card, actual account backup, real PIN or website was used. APP recovery implementation, real-card recovery and website login acceptance remain outstanding.
