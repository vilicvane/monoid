# Passkey architecture and iOS experiment lessons

## Current scope

The user clarified that direct NFC Passkey use was originally intended to come
from installing the corresponding FIDO applet on the card. Pause the iOS
credential-provider approach and focus next on remote use. Do not reinterpret
this as permission to store account private keys on the phone.

The initial cleanup left Home → Passkeys, local account management/storage and
Passkey-specific seed derivation/signing wrappers. The user subsequently
questioned these remnants, and cleanup was expanded to remove the entire app-level
Passkey experiment: Home entry, account pages, routes, storage service, request
and response wrappers, dedicated tests and product documentation. The local iOS
provider extension, App Group request store, native bridge and notification
handoff had already been removed. Preserve the original generic Monoid card
protocol, P-256 operations, Safe management and NFC session functionality.
There is no Passkey UI, registration/sign-in transport or credential-management
implementation in the app. Existing QR scanners advertise and process WalletConnect
only. Keep the lessons here rather than retaining unused experiment code.

Direct NFC requires a FIDO2/CTAP applet (standard NFC AID A0000006472F0001),
which is separate from the current Monoid applet's generic P-256 operations.
The sibling firmware repo is authoritative; its FIDO2 work was still marked
unfinished when investigated. Do not claim App changes alone implement it.

## What the physical experiment established

- Core NFC session initializers are unavailable to app extensions, including
  the newer configuration initializer in the inspected iOS 27.1 SDK.
- The user reached Monoid's system credential provider. `Check for approval`
  was only a poll; it did not open the main app or start NFC.
- Swiping to switch out dismissed the system sheet. A subsequent local
  notification experiment successfully opened Monoid, but the sheet disappeared
  during that switch and did not return when the user went back.
- Public UserNotifications APIs can navigate to the containing app. They do
  not establish preservation or resumption of an AuthenticationServices request.
  No public save/restore token was found on ASCredentialProviderExtensionContext
  or NSExtensionContext for the closed original request.
- Writing a signature into shared storage is only staging a result; it is not
  proof of delivery to the system or acceptance by the website. Do not display
  successful completion based solely on that write.
- `viewDidDisappear`, host background notifications, and process lifetime do not
  reliably prove system-request cancellation or liveness. Completion callbacks'
  `expired` argument describes extension cleanup execution time, not RP success.
- A new originating request may have a new challenge. Never revive/replay a
  previous signature to work around the lost context. Pre-reading a card public
  key cannot pre-sign future login challenges.
- Simulator compilation/unit tests did not validate the handoff. Simulator UI
  also exposed native no-argument resolve returning undefined and a missing
  credential-provider helper with a never-returning status callback. These were
  experiment-specific fixes, not reasons to retain the removed provider code.

The signed experimental version was installed on the physical iPhone. At the
user's subsequent request, the cleaned build replaced it on the same iPhone
and was launched successfully. Its signed package has no MonoidPasskeys extension
or AutoFill/App Group entitlements. No explicit migration or deletion of historic
device App Group metadata was performed; do not claim otherwise.

The expanded cleanup removing the Home entry and all remaining app-level Passkey
management/wrappers also passed the application suite (1791 tests) and a signed
iOS build, then replaced the iPhone installation and launched successfully.

## Remote feasibility research

Distinguish arbitrary remote transport from a browser's native FIDO QR flow.
The latter is CTAP hybrid and requires BLE proof of proximity in addition to
an encrypted data channel. Both QR-initiated and state-assisted linked-device
transactions use BLE advertisements. Internet data transport does not make
this proximity step optional.

The user successfully authenticated from Chrome's Windows system QR dialog
after tapping Bluetooth off in the iPhone Control Center, and clarified that
they did not switch it off in Settings. Apple documents that Control Center
disconnects accessories but leaves Bluetooth available for system features;
this observation is not a Bluetooth-disabled counterexample. A true comparison
must disable Bluetooth in Settings before starting a fresh request. Windows can
own the WebAuthn/CDA interface used by Chrome; do not describe every desktop QR
as Chrome's own transport implementation. Microsoft explicitly requires Bluetooth
on both devices for its cross-device passkey flow.

CTAP 2.3 section 11.5.1 specifies UUID 0xFFF9 with 20-byte service data.
Chromium's inspected v2 discovery reads that service data before establishing
QR tunnels or accepting linked devices. The QR is decimal-encoded CBOR carrying
connection keys and hints, not an RP request. The eventual authenticated channel
carries concrete CTAP requests/clientDataHash.

The inspected iOS 27.1 CBPeripheralManager and Apple's public documentation
only support advertising LocalName and ServiceUUIDs; they do not support the
required service-data payload. Moving bytes to LocalName or another UUID is not
compatible with Chromium. New hybrid BLE L2CAP channels still require the same
advertisement, so do not solve this issue. No complete iOS public-API path for
Monoid's own standard hybrid authenticator was found. Choosing Android, extra
BLE hardware, or a separate companion desktop transport changes the deployment
and requires an explicit product decision; do not silently substitute a custom
QR protocol or omit proximity while claiming native FIDO compatibility.

## Historical experiment design

The following records the removed design for future evaluation, not current
functionality or a requirement for the planned card FIDO applet. Do not assume
the applet will use this metadata format or derivation scheme.

- The experiment accepted only 64-byte Safe seeds, index `0240` plus sixteen hex
  digits. Its registration UI verified the chosen seed against a known wallet
  public key before enrollment. A generic master key had insufficient provenance
  to assume Monoid-001 derivation.
- Derive with `ASCII("Monoid-Passkey") || 00 || uint16be(length(UTF8(RP ID))) ||
UTF8(RP ID) || random 32-byte credential ID`. Seed index is not in the context.
  Check the saved compressed P-256 public key on every assertion.
- Keep ES256/COSE EC2, none attestation, zero AAGUID, UP/UV/BE, BS unset and a
  zero counter. Sign SHA256(authenticatorData || the actual clientDataHash) on
  the card, verify the compact signature, then DER encode. Binary outputs stay
  independent of provider/platform JSON, and no fake clientDataJSON is created.
- Obtain fresh request-bound user verification in the eventual transport/UI.
  Reuse the shared Access PIN/card session prompt with no automatic retry of
  operations. Keep cancellation checks at every card await boundary and publish
  durable metadata after NFC cleanup before delivering registration.
- The experiment stored only public metadata on the phone, never seed/private-key
  material. It serialized local writes and checked revision before publishing
  state. It had no metadata backup/export; a seed alone could not reconstruct
  random credential IDs or account discovery metadata. The account list did not
  enumerate or manage FIDO credentials inside a card applet.
- Apple engineer guidance in forum thread 745605 said both BE and BS are required
  for credential providers. This is an additional risk if that discontinued
  design is reconsidered. Never set BS without evidence of a complete backup
  just to pass a platform check.
