# Unlock saved PINs before manual PIN input

## Requirement

[user] When the current operation requires both unlocking saved PINs and
manually entering a PIN, unlock first and show PIN input afterward. Apply the
same order across the relevant flows.

## Scope and implementation

[agent] Unlocking here means authorizing the phone's protected Access PIN
storage. It does not replace authenticating the card on each NFC tap.

- Card Applets installation, maintenance, recovery and PIN setup authorize the
  existing PIN session before asking for the Secret PIN.
- Resetting a card before adding it to a new or extended bundle unlocks before
  asking for the new Secret PIN. The same session covers removing the old card's
  saved Access PIN and saving the replacement card's PIN. An already attempted
  reset keeps its existing recovery behavior; do not add another unlock merely
  to check its outcome.
- Access PIN changes and initialization of an unset Access PIN preload through
  `MonoidPINSession.getPINs` before manual input, then save through the same
  session after card confirmation and NFC cleanup. This preserves the existing
  manual fallback when protected storage is unavailable. A local save failure
  does not undo a confirmed card update.
- Copy and Sync steps that only require a Secret PIN do not gain a vault prompt.
  Security Key and ordinary Access PIN scans already preload before input.
  Setting or changing only the Secret PIN does not require vault access.

## Lifecycle

[agent] Check cancellation and page activity after unlocking and before opening
input or starting NFC. Cancelling the unlock or leaving the page must not open
a late input or scanner. Clear a failed unlock session before rethrowing so a
later explicit retry does not reuse its rejected authorization promise.

Successful borrowed sessions remain owned by their page; temporary sessions
are disposed when their operation ends. Reuse valid authorization for saving.
Keep the existing authorization expiry, background revocation and manual
fallback rules. Secret PINs remain unpersisted.

## Saving after authorization expires

[user] Accepted reauthorizing when the Access PIN save fails because the initial
biometric authorization expired, then retrying only the local PIN save.

[agent] `MonoidPINSession.setPIN` renews once on `AUTHORIZATION_EXPIRED` and
retries its local read/merge/write. The 60-second native lifetime is unchanged.
The native expiry result guarantees no write committed; other errors, including
ambiguous storage failures, cancellation, background revocation and closed
access, do not trigger renewal. A second expiry or a rejected new unlock returns
to the existing save-failure handling without another prompt.

Dispose the expired access and share the replacement authorization among
concurrent saves. Keep the same page-owned signal and temporary PIN cache;
check cancellation before unlocking and retrying. Snapshot freshness still
uses the store's serialized read/modify/write and revision checks. No card
operation, scan, PIN change, installation or recovery is repeated. Saving
still takes place after NFC and its presentation finish. Other operations such
as reading or removing saved credentials do not gain automatic renewal.

## Android keyboard handoff

[user] After biometric unlock, the PIN input can have focus without opening
the keyboard.

[agent] Captured this on Android: the password input received DOM focus 4 ms
after vault authorization resolved, but no keyboard-show event followed. An
explicit keyboard request opened the IME for the same input without changing
focus. `document.hasFocus()` remained true throughout, so it cannot establish
whether Android has finished handing back native window/IME focus.

Keep the per-instance input remount and unlock-before-input order. The shared
input modal explicitly requests the Android keyboard once per editable prompt.
The native request waits for the captured view's window focus and posts its IME
request after focus is ready, instead of using a fixed delay. Closing, aborting,
replacing or unmounting the prompt cancels an outstanding request; native view
focus loss, detachment, stop and destruction also cancel it. Do not blur/refocus the
input, because the existing blur handler cancels the modal. Do not reopen the
keyboard when the user dismisses it. iOS/web retain their autofocus behavior.

## Verification

[agent] TypeScript and focused component tests cover prompt order, cancellation,
page exit, retry after failed unlock, shared-session saving and unavailable
storage. Physical NFC mutations were not repeated as part of the keyboard fix.

[agent] The keyboard regression was reproduced on the physical Android phone.
TypeScript, 58 focused input/PIN tests, 13 native keyboard tests and the Android
debug build passed. The updated debug package was installed with app data
preserved. The user confirmed that the keyboard now opens after biometric
unlock; the trace recorded input focus, `keyboardWillShow` 104 ms later, then
`keyboardDidShow`. Closing the input produced the normal hide events. Temporary
diagnostics were removed; they recorded no PIN values or credentials.

[agent] The expired-save renewal passed TypeScript, formatting/diff checks and
407 focused credential, PIN, setup, bundle and Card Applets tests. Coverage
includes expiry during read/write, a second expiry, cancellation before/during
renewal, concurrent saves sharing the new unlock and preserving unrelated
credential changes. The development server serves the updated implementation;
the timed expiry path has not been repeated with a physical biometric prompt.
