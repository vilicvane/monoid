# 多卡同步

更新日期：2026-10-25。

本文记录 Safe → Card 中多卡同步的范围、合并规则和验收条件。它同步卡片上实际存在的资源，不自动导入手机，也不把手机尚未上传的 Alias 或地址变动加入结果。手机与单卡之间的下载合并、上传替换仍遵循[地址管理规则](address-management.md)。

## 同步范围

一次同步可以包含不同 Bundle 的卡和未加入 Bundle 的卡。参与同步不改变卡片的 Bundle，也不重置、安装或更新 Applet。

合并身份为 `scope + resource index`，不能只按 index 或公钥判断。普通共享数据使用全局范围；Secret 及其附属记录使用所属 Bundle 的范围。未加入 Bundle 的卡使用本卡范围，Secret 不传到其他卡。

| 资源                                      | 参与范围               | 读取和传递                                 |
| ----------------------------------------- | ---------------------- | ------------------------------------------ |
| 没有关联 Secret 的普通数据                | 本次所有卡片           | 明文读取、合并后写入                       |
| Security Key 凭证 `0xf101`                | 本次所有卡片           | 公共记录，校验格式后按 index 补齐          |
| Bundle 内的 Secret                        | 本次相同 Bundle 的卡片 | 使用卡端加密导出、导入，不读取 Secret 明文 |
| 未加入 Bundle 的 Secret                   | 仅原卡                 | 保留原卡内容，不跨卡传递                   |
| Secret 的附属记录，包括 `0x0f01` 地址清单 | 与主资源相同的范围     | 可以明文读取，但不能因此扩大同步范围       |

派生记录的关联以完整源 index 及经过校验的记录内容为准。找不到主资源的附属记录不能作为普通全局数据传播。不同范围中碰巧相同的 index 或公钥不能连接两个范围；某目标卡已有相同 index、但属于不同范围时，也不能借覆盖或改 `secret` 标记完成同步。

当前 App 定义并识别的附属类型是地址记录 `0x0f01`。新增附属类型时必须同时定义其主资源关联与同步范围；普通资源的 metadata 不能未经类型规则就被解释成这种关联。

OTP 账户 `0xf201` 自身就是一个 Secret 资源：data 保存 HMAC secret，metadata 保存算法、位数和周期，alias 保存标签。它没有附属 HMAC 项或 key reference；Copy 通过加密 Export/Import 传递单个账户，Sync 按账户本身的 Secret 范围传递。卡端校验的 index 为 `f201 || SHA-256(secret)[0:8]`，相同 index 固定相同 secret；只比较配置，不比较加密信封。配置不同即冲突，Alias 仍按既有规则合并；无需通过重复导入核验已有 OTP 副本。

`0xf101` 是公共凭证记录，不是 Seed 的附属资源。它携带的凭证 scope 不改变上面的 Secret 同步范围，也不能用于反推或自动携带某个本地 Seed。

卡片身份绑定完整公钥，不能只使用界面显示的短 ID。写入前重新核对卡片身份及 Bundle；改变身份或 Bundle 后需要重新读取并生成计划。

## 合并规则

### 固定添加顺序

从 Card 进入的卡是第一张；后续卡按成功加入的顺序排列。重新扫描和写入顺序不改变优先级。收集完成后固定参与卡片和合并结果，再开始写入。

Alias 取该范围内、该资源按添加顺序遇到的第一个非空值。第一张卡没有 Alias 时可以采用后续卡的 Alias；全部为空时保持为空。空 Alias 不作为向其他卡传播清空的命令。

例如卡 A、B、C 的同一资源 Alias 分别为空、`Personal`、`Savings`，合并结果为 `Personal`。先写 C 再写 A 不会改变这个结果。

### 只合并，不传播删除

资源集合和可合并的地址清单取并集。某张卡没有资源、没有附属记录或清单为空，都不能解释成要求删除另一张卡的内容。

已记录的空清单仍然不同于从未创建记录。所有参与副本都为空时，保留有效空记录；另有非空记录时，合并为非空清单。没有记录时不会生成默认派生地址，也不会将界面预览加入同步。

因此，某地址只从一张卡删除后，再与仍保留该地址的卡同步，会恢复该地址。本功能不引入删除标记或跨卡删除传播；需要以手机清单替换单卡时，仍使用明确的 Update card 操作。

### 具体地址的身份

`0x0f01` 按源 Key index、address type 和完整派生参数合并。EVM、SegWit、Taproot、Solana 或不同 path 是独立记录；公钥相同不能把它们合成一条，也不能自动展开其他地址。

同一清单内的原生地址和派生地址继续使用已有记录格式。不保存手机的 default 选择、公钥缓存或未导入的预览状态。

### Security Key 凭证

`0xf101` 使用 `secret = false`。当前 CBOR 记录包含必填整数字段 `10`，值为 32 字节 scope；metadata 为 `scope || SHA256(rpId)`，共 64 字节。资源 index 仍为 `f101 || credentialId[0:8]`，完整 Credential ID 为 32 字节。Copy 和 Sync 都校验当前格式、index 和 metadata；旧版缺少 scope 的记录及畸形记录逐条跳过，其余记录继续处理，不自动迁移。

凭证 scope 是 Seed 内容和授权 domain 对应的稳定派生身份，与本地 Seed index、卡片 ID 和安装 token 无关。相同配置在不同卡上得到相同 scope；更换 Seed 内容或 domain 后，其他 scope 的记录仍保留，但不会被当前 Security Key 查找或注册替换。切回原配置后可再次使用。它与本文用于限制 Secret 传输的同步范围是两个概念。

不同 index 的凭证分别保留并补齐，不按 RP、user ID、账户名称或 scope 去重，不推断哪条较新或失效。同一 index 只有 metadata、Secret 属性和完整正文一致时才可视为同一份；不一致即冲突，不能按添加顺序覆盖。Alias 不参与凭证正文比较：Sync 取第一个非空值，Copy 跳过相同凭证并保留目标已有 Alias；Copy 其他类型的元数据冲突处理不变。没有删除标记，不传播删除。

Copy 和 Sync 不迁移 Applet grant，不自动授权、切换 Seed 或修改 domain。公共凭证可以跨卡共存，不意味着目标卡已经能使用它们；目标卡仍需对应 Seed 内容、domain 和本卡授权。Secret Seed 的传输保持原边界：Sync 仅在同 Bundle 内传递，Copy 仅使用原协议允许的加密导出、导入范围。

### 普通内容与结构冲突

仅对已定义合并规则的类型进行内容合并。其他非 Secret 数据在同一范围、同一 index 下，以第一张具有该资源的卡的完整内容为准；不会尝试拼接或解释未知格式。内容和 Alias 独立选择，所以结果可以使用第一张卡的内容和后续卡的第一个非空 Alias。

类型、metadata、Secret 属性或所属关系不一致属于结构冲突，不能用第一张卡的值直接覆盖。不同范围的同 index 同样不能覆盖。遇到这些冲突时，保留原数据并报告冲突，不能先删除再重建来绕过。

Secret 不能明文读取，也不采用第一张卡直接覆盖其他副本。支持读取公钥的 Key 使用实际公钥及相关派生材料校验副本一致性；seed 的链码也必须一致。

未知 Secret 类型在同一 Bundle 内有同 index 的多个副本时，元数据必须完全一致，包括 Alias。每张已有副本的卡使用另一张卡的导出包，通过卡端幂等导入核验正文：一致时不改写，不一致时报冲突。这些卡即使没有内容需要更新，也必须再次扫描核验；不能仅凭元数据一致直接显示完成。只有一个来源的 Secret 则直接使用加密传递。

未知 Secret 的 Alias 等元数据不同会阻止同步，本轮不临时改名来绕过导入校验，也不能对它使用首个非空 Alias 合并。这是当前协议下的明确限制。

## 执行和中断

1. 收集卡片：先输入将要刷的卡的 Secret PIN，再扫描读取当前卡片内容、Bundle 和附属关系。Card 页已有的列表快照不等于已读取全部数据，仍需取得本次同步需要的明文与加密导出结果。
2. 生成计划：按固定添加顺序和同步范围计算各卡的目标内容。无变化且不需要 Secret 正文核验的卡不要求再次扫描。至少两张卡均无需同步时，直接以普通的返回按钮替代 Continue，不进入 Complete；仍可继续添加、移除或重新读取卡片。从 Card 进入时，无需同步和同步完成都优先 Back to Card，没有对应历史时才 Back to Safe；独立入口直接尝试 Back to Safe，都无法返回时不显示返回按钮。
3. 写入：先输入将要刷的卡的 Secret PIN，再扫描任意尚未完成的卡。核对身份及 Bundle 后直接执行固定计划，不在写入前后全量复读。先完成本卡未知 Secret 的正文核验，再进行修改；先确保主资源存在，再写入附属记录。进度和卡片快照按成功响应更新，最后一项确认后即可标记完成。
4. 更新预览：写入原 Card 页对应的卡成功后，直接使用已确认的资源及派生记录，复用同一源 Key 的已知公钥，仅派生缺失的地址预览，再更新该页的完整 CardStore 缓存。不重复 List 或读取派生记录；添加卡和写入其他卡时不读取地址预览。

多卡写入不是跨卡事务。中断不会回滚已经完成的卡或项目；本页保留本次流程的结果和未完成部分，重新扫描后继续。只有某项命令响应丢失、结果不确定时才核对该项：普通创建及修改通过 View 和必要的数据读取判断是否成功，不重读其他项目；Secret 导入及正文核验使用原导出包的幂等导入确认或完成，不盲目重放普通创建。

同步期间参与卡片只由当前流程操作，合并来源固定为收集阶段读到的快照。不检测其他流程或设备对内容的并发修改，也不为此重复读取清单、数据或 Key 指纹。每次刷卡仍核对完整身份及 Bundle，避免误刷其他卡。

收集阶段保留原 CardStore 缓存。收到写入成功响应或重新读取确认后，使对应卡的旧缓存失效；已确认的内容和进度仍保留在同步会话中。只有完整地址预览读取成功才重建 CardStore；若读取中断，返回 Card 页后沿用重新扫卡入口，避免把未读取的地址误当为空清单。其他卡被写入后的旧缓存同样失效，但不额外预读地址。

计划中的结果不能提前作为卡上事实；后续失败也不能隐藏之前已经确认的写入。WalletStorageService 中手机已导入的 Key、地址、Alias 和默认选择不由此流程更改。

收集与写入阶段都在刷卡前输入 Secret PIN，直接取得读取、导出和写入权限，不读取保存的 Access PIN，也不进行额外 Access PIN 认证。包括仅同步普通数据的卡，也使用同一认证流程；Secret PIN 不持久化，每次需要读写的刷卡均重新认证。

已完成或无需变更的卡再次刷入时，在核对完整身份及 Bundle 后显示 `Already synced` 并结束本次扫描，不再认证、读取资源或刷新地址预览。流程数据不构成跨重启的恢复存档，也不承诺退出本次流程后能够继续。

## Bundle 卡更新与重装

Card Applets 在更新或重装 Monoid 时复用上述合并算法，并把本卡的写入延后至安装完成。只更新 Security Key、没有替换 Monoid 存储时，不需要这个同步步骤。Fresh install 会更换 Identity，不使用此恢复流程。

1. 读取待更新卡 A 的资源和原 Applet 授权范围，把 A 作为第一张卡加入同步，保留首个非空 Alias 的优先级。
2. 添加一张或多张同 Bundle 卡，使用现有规则合并所有参与卡的资源，并按添加顺序处理 Alias。其余卡可以任意顺序刷入，直到各自的同步计划完成；A 的写回仍留到安装后。不同 Bundle 或 A 自身不能作为恢复来源。
3. 所有其余卡同步完成后，从最后刷入的卡重新导出完整合并结果。如果这些卡均无需写入，则任选一张认证并导出；导出中断后也可换另一张已同步卡重试。仍有卡待同步时，刷入已完成的卡只提示 `Already synced`，不提前准备恢复档。不能使用可能由 A 签发的旧缓存包，因为 A 不能导入自己的 Bundle 导出包。
4. 校验来源身份、Bundle、包头、元数据及导入大小，持久化完整加密恢复档并读回核验后，返回 Card Applets。用户再次明确执行更新或重装，才开始删除 Applet。
5. 安装后向 A 全量导入恢复档，不能继续 A 之前的增量计划。核验资源后，一次性检查所有待恢复授权依赖的 Seed／Key 和目标 Applet 实例，再恢复 A 原有授权范围；不复制 B 的授权或安装 token。

准备同步期间只保留当前内存流程，不保存 PIN；失败不会触发本卡重装。完整恢复档保存后保留至恢复和授权核验成功，退出或重启后可从 Card Applets 继续。已经完成重装但尚未恢复的 Bundle 卡，同样通过 `Sync items` 从另一张成员卡准备恢复档，随后只导入数据和恢复授权，不再次重装。

维护同步返回 Card Applets 时带回本次扫描的卡片信息；该快照只用于这次路由往返，不保留到新的独立入口。准备同步中的 `Start over` 清除本次收集并返回 Card Applets，可重新发起操作，已经写入其他卡的内容不回滚。恢复档已保存、尚未开始替换时，按钮显示 `Continue installation`／`Continue update`，表示继续已准备好的安装或更新流程；点击后仍需确认。菜单仍允许确认 `Start over` 后清除准备档。只有 `ready` 且无替换检查点的任务允许清除；开始替换后显示 `Resume reinstall`／`Resume update`，保留恢复材料，不能通过 Start over 丢弃。

这里持久化的是同卡维护所需的加密恢复材料和公开授权范围，普通 Sync 不因此增加持久化或跨卡授权迁移。

## 验收场景

1. 同 Bundle 两张卡各有不同 Secret 和地址记录：完成后两卡在该 Bundle 的范围内取并集。
2. Bundle A、Bundle B 和未加入 Bundle 的卡混合：普通数据可以互通，Secret 和附属记录不跨范围。
3. 非 Bundle 两张卡：普通数据同步；各自 Secret 和地址记录保持本卡，不因此建立 Bundle。
4. 同 index 出现在不同范围：不覆盖、不改变 Secret 属性，也不借相同公钥转移附属记录。
5. 第一张卡 Alias 为空、后续卡非空：采用第一个非空值；写入顺序及中断重刷不改变优先级。
6. 地址清单分别为 `{A, B}` 和 `{A, C}`：结果为 `{A, B, C}`；已有空记录与非空记录合并也不传播删除。
7. 孤立、损坏或所属关系不一致的派生记录：不能作为普通数据跨范围同步。
8. 写入过程中掉卡或取消：保留已确认进度；重新读取可以确认响应丢失但已成功的写入，不重复创建资源。
9. 正常写入不重复调用 List、Get 或 ViewKey，也不显示 Checking card；身份或 Bundle 不匹配时仍在修改前拒绝。中断重试只核对未收到成功响应的那一项，已确认项目不再复读。
10. 同步结束后，手机已导入地址不增加、不删除；手机尚未上传的变更也不影响本次结果。
11. 两张同 Bundle 卡有同 index、元数据一致的未知 Secret：两张卡都通过另一张卡的包核验正文；不一致时报告冲突且不覆盖。Alias 不同时在生成计划阶段报告无法比较，不临时改名。
12. 同一 RP、同一 user 的不同 Credential ID，以及不同凭证 scope 的记录，都按独立 index 保留；同 index 的正文或结构差异报告冲突。
13. 缺少 scope、scope 长度错误、metadata 或 index 不匹配的凭证逐条跳过，其他记录继续 Copy 和 Sync，不做旧格式迁移；公共凭证传递不扩大 Secret 范围，也不迁移 grant。

## 不兼容记录

Safe、OTP、Copy 和 Sync 的集合读取只跳过本地格式不兼容的单条记录，包含无法解析的派生记录、OTP 账户、Security Key 凭证及无效关联。原卡数据不删除，未知但可原样传递的自定义类型仍保留。目标卡跳过的 index 仍视为已占用，不能当作缺失项而被覆盖。

断卡、PIN／权限失败、取消及结果不确定的写入继续中止；合法记录之间的冲突仍按原有规则处理。完整重装前的恢复存档不能使用有遗漏的列表冒充完整备份。

卡片协议只使用 `metadata`／`metadataPrefix`，临时旧字段转换已移除。已有维护存档的落盘字段映射独立保留，不改变归档正文、加密包或校验值。

## 验证边界

以上是本功能的行为约定及验收条件。自动测试和模拟卡可以验证合并、范围隔离与中断状态处理；不能替代实际卡片的容量、加密传输、PIN、掉卡和多卡轮换验收。本次文档不宣称已完成实卡验证。
