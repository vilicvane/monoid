# 地址管理与卡片同步

更新日期：2026-10-19。

地址是导入、删除和同步的独立单位。Key 提供产生地址和签名的能力，公钥是地址的计算材料；公钥相同不能扩大导入范围或让不同地址共享删除状态。

本文记录已确定并实现的地址管理规则：下载合并、上传替换；派生与原生 Key 都使用明确的地址清单，卡片记录随 Copy 携带。下文的验收场景定义这些行为的预期结果。

## 已确定的原则

### 地址的身份

- 一个地址记录属于一个源 Key，由源 Key 的 index、address type 和实际派生参数共同标识。派生参数包括 seed 转换方式、派生算法或 curve，以及完整 path；原生 Key 没有 path。
- EVM、Bitcoin Native SegWit、Bitcoin Taproot、Solana 是独立的 address type。即便共用公钥，也分别保存、导入、删除。
- 不按公钥合并地址记录，也不因为一个公钥能够计算其他类型的地址，就自动将它们加入手机。
- 当前 EVM 是一个地址类型，不按 Ethereum、各 EVM 链的 chain ID 重复保存同一条地址记录。网络筛选中的 BTC 也只是分类，不能抹掉 SegWit 与 Taproot 的区别。
- 可以复用已知等价的派生请求或公钥，减少刷卡与计算；优化完成后仍返回各自完整的地址记录。Taproot tweak 等会改变输出公钥的参数必须参与请求等价判断。
- 相同完整地址身份或等价底层请求若返回不同公钥，应报告数据不一致，不能按“新地址”静默掩盖问题。仅路径相同并不足以判断等价，例如 Taproot tweak 可以正常改变输出公钥。

### 三种不同状态

| 状态           | 含义                                                  | 持久化位置                             |
| -------------- | ----------------------------------------------------- | -------------------------------------- |
| 地址预览       | 为展示读取的公钥与地址，包括未记录 Key 的默认路径预览 | CardStore 内存                         |
| 手机已导入地址 | 用户明确导入或在卡片更新操作中合并到手机的地址        | WalletStorageService                   |
| 卡片已记录地址 | 与源 Key 关联、可以随 Copy 携带的地址参数清单         | 卡片附属记录，当前为 `0x0f01` 派生记录 |

读取或切换预览不会自动导入，也不会自动增加卡片记录。手机已删除的地址即使仍能从卡上计算出来，也不能仅因预览或缓存命中重新成为已导入地址。

### Default 仅属于手机

`defaultWallet` 是手机的展示偏好，不写入卡片，也不随 Copy 同步。默认展示哪条地址和地址清单包含哪些条目是两个问题。

删除默认地址时清除该引用，由仍存在的地址提供界面回退；不能为保留默认展示而阻止删除或偷偷恢复地址。同步时保留仍有效的本机默认选择。

## 创建和导入

### 创建 Key

创建流程为：创建卡内资源 → View 元数据 → 读取所选网络的地址或公钥 → 成功结束扫描 → 自动勾选新增 Key。

自动勾选只追加新 index，保留此前选择。创建已确认但后续读取失败、取消或页面离开时，保留已确认的卡片项目，不将该流程视为成功并自动勾选。创建本身不自动 Import，也不自动保存预览地址的派生记录。

secp256r1 目前可创建和读取公钥，但没有钱包地址适配；自动勾选不意味着它获得 Import 能力。选择项中含不可导入的资源时，仍遵守现有的操作可用性规则。

### 单地址导入与卡片清单导入

导入范围由用户选择的对象决定，不由按钮写着 Import 还是 Update 决定：

- Card 页面勾选带有已保存地址清单的 Key，并选择卡片 → 手机：导入该 Key 的记录集合。新手机显示 Import，已有 Key 时显示 Update，两者都允许合并完整卡片清单。这保留了换手机时一次导入全部已记录地址的行为。
- Key 页面 Derive 后导入、Card 中没有地址清单时导入当前预览、以及新建 Key 后导入：仅导入本次明确选择的地址。为保留其他卡片记录，写卡可以使用并集，但不能把写入函数返回的整个并集全部加入手机。
- Card 已有记录，同时切换到未记录的预览地址时，先处理明确的卡片清单下载，再另行处理该预览地址的新增导入；延续现有分步规则。切换预览不应悄悄扩大整项下载的范围。

例如手机删掉 A 后又在 Key 页面派生并导入 B：手机只新增 B；卡上尚存的 A 可以继续存在，直到用户明确选择从手机更新卡片。用户另行选择该 Key 的卡片清单下载时，才主动将 A 合并回手机。

## 删除地址

删除具体地址只移除手机上的该地址记录，不删除源 Key、Alias、卡内私钥或其他地址。公钥缓存仍可保留供计算复用，但缓存存在不能决定哪些地址已导入。

seed、master、原生 secp256k1 和 ed25519 使用相同的明确地址列表及删除规则。原生 Key 不再从一个公钥自动展开多种已导入地址。

删除最后一个地址后保留没有地址的 Key。seed/master 可重新 Derive 后导入；原生 Key 页面显示 Scan card，进入现有刷卡流程重新导入。整项删除 Key 和删除卡片资源继续属于独立操作，不依赖自动展开公钥重新填满列表。

删除本机地址不会自动移除 WalletConnect 已授权的账户。账户解析和签名以当前明确保存的地址记录为准；若没有其他已导入记录提供同一链上的同一地址，会话和待处理请求显示账户不可用。若另一条已导入记录仍能提供该地址，可以重新解析并使用那条记录；不能仅凭另一个公钥相同就恢复被删记录。

已打开的请求页面和异步签名流程也会核对具体 Key 与地址参数。先前解析的记录被删除后，不能在等待刷卡或读取公钥期间改用另一条记录继续原操作；在发送签名命令前重新核对，已发出的签名命令则无法因随后删除记录而回滚。远端会话更新和断开保持独立策略，不把删除本机地址等同于撤销外部会话。

## 同步方向的交互

点击每个 Key 标签栏中的更新标记，可手动指定卡片 → 手机或手机 → 卡片的可操作方向，底部按钮随之变化。切换方向只修改本次操作选择，不立即读写，也不改变勾选状态。

卡片 → 手机沿用原有更新标记；手机 → 卡片使用另一配色的上箭头。只有实际存在差异且两端具备对应数据时才提供切换。没有手机 Key 时只能 Import，不能把“未导入”当作“删除全部地址”上传空清单；两端一致时显示 Saved。

每个 Key 独立选择方向。多选时，Import/Update 只处理选择了卡片 → 手机的项目，Update card 只处理选择了手机 → 卡片的项目；两个按钮按各自是否有可操作项目出现。一个项目需要下载，不会禁用其他项目的上传。

同一个 Key 的 Alias 与地址清单使用同一方向。默认方向只是初始选择，不阻止用户选择另一可操作方向。完成操作或重新扫卡后根据新数据重新计算；操作中禁用方向切换。

## 同步集合的规则

记手机已导入清单为 P，卡片已记录清单为 C，预览地址不属于这两个集合。表格描述两端已有清单的情形；`C = undefined` 表示尚无记录，`C = ∅` 表示已有明确空清单，两者不能被集合比较或 Saved 判断混为一谈。手机没有 Key 同样不同于已有 Key 的地址列表为空。

| 操作                      | 手机结果  | 卡片结果  | 用途                                           |
| ------------------------- | --------- | --------- | ---------------------------------------------- |
| 单地址 Import X           | `P ∪ {X}` | `C ∪ {X}` | 新增明确选择的地址，保留其他卡片记录           |
| 卡片 → 手机 Import/Update | `P ∪ C`   | C         | 延续此前允许手机合并的规则                     |
| 手机 → 卡片 Update card   | P         | P         | 以手机清单替换卡片清单，使本机删除能够同步回卡 |

例如 P = {A, B}、C = {A, C}：下载得到手机 {A, B, C}；选择上传则卡片变为 {A, B}，卡上独有的 C 会移除。

上传替换无法凭集合差异区分“用户故意删除 C”和“用户从未导入 C”。用户手动指定手机为来源，代表这次认可手机清单为准；如果希望保留 C，应先执行下载合并。界面应能让用户理解上传会移除卡上独有记录，不能只改箭头而继续执行并集。

### 空清单和没有清单

两者严格区分：

- 没有卡片附属记录：尚未记录地址选择，可以提供默认地址预览；预览仍不是已导入条目。
- 已有附属记录但清单为空：明确记录零个地址，不能恢复默认地址；卡片仍保留源 Key，并允许手动预览或重新添加。

因此上传空清单会保留一个有效的空附属记录，不会删除记录后又按“首次使用”回退。Copy 携带这个空记录及其与源 Key 的关联；源卡没有附属记录时，不删除目标卡已有的附属记录。

### 执行和中断

- 需要追加卡片记录的单地址 Import，在刷卡时读取最新清单并合并，避免覆盖其他设备新增的记录。导入已经读出的完整卡片清单，如果没有需要写卡的内容，可以直接保存手机，不额外要求二次刷卡。
- 覆盖上传先绑定完整卡片身份，并核对当前清单与用户选方向时看到的清单；若已经等于本次目标，视为目标已达成；若与快照和目标均不同，提示重新扫卡，取得新快照后再选择方向，不能用过期快照覆盖新的地址。
- 每个 Key 的已确认写入独立提交到 CardStore；后续项目失败不能回滚或隐藏前面已经成功的写入。
- 响应丢失时重新读取并核对结果，不自动重建 Key，也不把一次不确定写入当作未发生。
- CardStore 表示最近读取或确认写入的卡片快照，不会自动获知其他设备的写入。手机删除只修改手机地址列表，不能先修改 CardStore 假装已完成同步。
- Copy 复制卡片的实际资源及附属清单，手机尚未上传的增删不能自动改变复制内容。保留主项与附属记录成组操作、`2+2` 数量和导出导入合并分母的规则。源卡有记录时会携带该记录，包括明确空清单；目标卡同一 index 已有不同内容时，沿用现有冲突提示并保留目标内容，不自动覆盖。源卡没有记录时，不删除目标卡已有的附属记录。Copy 的冲突处理与 Update card 的明确上传替换是不同操作。
- Alias 独立于地址集合处理：`undefined` 表示本次未提供 Alias，保留本机值；`''` 表示明确清空。卡片下载将无 Alias 规范化为 `''`，使清空也能同步；上传同样使用本机 Alias 的明确值。

## 卡片记录格式

`0x0f01` 保存所有当前支持钱包地址的 Key 的地址清单，包括 seed/master 的派生地址和原生 Key 地址。版本和外层格式为：

```text
[1, sourceIndex, [[type, addressType, binaryPaths], ...]]
```

seed/master 的算法名继续为 `bip32` 或 `slip10-ed25519`，path 每一级使用 4 字节，已有组的编码保持不变。原生 Key 使用对应算法名 `secp256k1` 或 `ed25519`，该组的 paths 为 `[]`，表示一条没有派生路径的具体地址；例如 `['secp256k1', 'evm', []]`。

类型和源 Key 必须匹配。原生 `secp256k1` 可记录 EVM、SegWit、Taproot，原生 `ed25519` 可记录 Solana；secp256r1 当前没有钱包地址类型，不纳入记录。原生组的空 paths 和整个 payload 的空 groups 有不同含义：前者是一条原生地址，后者是明确零条地址。

记录仍不保存公钥或本机 default。主项和附属记录的关联、Copy 成组携带、删除附属项优先等规则统一适用于派生与原生 Key。本次使用现有 Safe 资源读写能力，不调整固件 APDU。

## 手机存储与旧数据迁移

所有 Key 都通过 `wallets` 数组保存明确地址记录，`getKeyWallets` 只根据这些记录生成地址视图。公钥不再作为根字段决定已导入地址，也不单独保留第二套导入状态。

加载持久化数据时，仅对仍带有旧根字段 `publicKey` 或 `taprootOutputKey` 的 Key 执行一次迁移：原生 secp256k1 的 `publicKey` 转为此前已展示的 EVM 与 SegWit 记录，`taprootOutputKey` 转为 Taproot 记录；原生 ed25519 的 `publicKey` 转为 Solana 记录。已有明确记录和有效的本机 default 保留，同一请求的公钥不一致会报错。

迁移后的地址清单会先持久化，并移除旧根字段，再用于初始化存储服务；持久化失败会报告错误，不静默使用未保存的迁移结果。没有旧根字段的 `wallets: []` 是有效空清单，后续加载不会再次展开地址。

## 验收场景

1. 创建并成功读取 Key 后追加勾选；保留旧选择，不自动 Import。创建已确认但读取失败时保留项目，不自动勾选。
2. 同一个公钥对应 EVM 与 SegWit：只导入 EVM 时只出现 EVM；单独导入 SegWit 后有两项；删除任意一项不影响另一项。
3. 相同公钥、不同 address type 或不同 path 的派生记录不合并；等价的底层读取可以减少为一次。
4. 手机删除 A，随后在 Key 页面派生并导入 B，A 不被自动加回；用户在 Card 页面明确下载整个 Key 的记录清单时可以恢复 A，新手机的 Import 也能导入完整清单。
5. P = {A, B}、C = {A, C} 时可以切换两个方向，结果符合已经确认的同步表；两端集合大小相同不代表一致。
6. 手机仅少了卡片中的一项，没有新增项，也应能选择上传传播删除。
7. 多个 Key 可以选择不同方向，操作按钮只处理自己方向的项目。
8. 删除最后一个地址保留 Key；上传空清单并重新扫卡后仍保持空清单，不自动恢复默认地址；Copy 到没有目标冲突的卡片后同样保持空清单。
9. 本机 default 不出现在卡片记录中，跨手机导入不覆盖有效的本机偏好。
10. 写入前卡片被另一设备修改时不静默覆盖；中断后保留所有已确认完成的项目。
11. 已删除记录不能再发起本地签名；若没有其他已导入记录提供该链上的同一地址，旧会话及已打开的请求页面明确显示账户不可用。异步流程在发出签名命令前重新核对；不宣称能撤回已发出的命令。
12. 原生 Key 的地址清单与派生地址使用相同的 Copy 规则；源有空记录时携带空记录，目标同 index 内容冲突时提示并保留目标，源无记录时不删除目标附属记录；secp256r1 不因本次调整被误认为支持钱包地址。
13. 旧原生数据迁移保留此前可见的地址和有效 default，并移除根公钥字段；之后删除所有地址再重启，Key 仍为空，不会重新迁移或恢复已删除地址。
